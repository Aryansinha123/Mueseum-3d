# AR PERFORMANCE OPTIMIZATION + INSTANT MARKER FIX

## OBJECTIVE

The current Virtual Museum / AR website is functional, but the experience is too laggy.

The biggest problems are:

1. AR mode feels slow and laggy.
2. 3D artifacts do not render smoothly enough.
3. The yellow placement/selection marker does not appear instantly.
4. There may be unnecessary React re-renders.
5. GLB models may be loading/reloading unnecessarily.
6. AR interactions such as rotate, scale, and move should feel much smoother.
7. Opening AI Curator must not freeze or interrupt the AR experience.

The goal is:

> **Make the existing museum and AR experience feel smooth, responsive, and production-quality without changing the core functionality.**

DO NOT rebuild the entire project.

DO NOT replace the existing AR system unless the current implementation is fundamentally broken.

First diagnose the actual bottlenecks, then optimize them.

# 2. FIRST PRIORITY — FIX YELLOW MARKER DELAY

The yellow marker must appear **immediately when a valid AR surface/hit-test result is detected**.

Current problematic flow may be:

```text
AR detects surface
      ↓
wait for artifact GLB
      ↓
wait for React state
      ↓
render marker
```

This is wrong.

The marker should NOT depend on the artifact model loading.

Correct flow:

```text
AR starts
   ↓
Hit-test detects surface
   ↓
IMMEDIATELY render yellow marker
   ↓
User taps
   ↓
Place artifact
   ↓
Load/render GLB
```

The marker and artifact loading must be independent.

---

# 3. MARKER MUST BE A LIGHTWEIGHT OBJECT

Do NOT use a heavy GLB or complex component for the yellow marker.

Use a lightweight Three.js primitive.

For example:

```text
RingGeometry
CircleGeometry
PlaneGeometry
Line
MeshBasicMaterial
```

Prefer:

```js
MeshBasicMaterial
```

because it does not require lighting calculations.

The marker should be extremely cheap to render.

Example concept:

```js
const geometry = new THREE.RingGeometry(0.08, 0.1, 32);

const material = new THREE.MeshBasicMaterial({
  color: 0xffff00,
  transparent: true,
  opacity: 0.85,
  depthWrite: false
});
```

Adapt to the existing project's scale.

DO NOT blindly copy this exact code if the project already has a marker implementation.

---

# 4. MARKER MUST BE PERSISTENT

Do not create and destroy the marker every frame.

BAD:

```text
Every frame
 ↓
create marker
 ↓
render
 ↓
destroy marker
```

GOOD:

```text
AR starts
 ↓
Create marker ONCE
 ↓
Every frame:
   update position
   update visibility
```

Create the marker once and reuse it.

---

# 5. USE REFS FOR REAL-TIME AR STATE

Do not cause React re-renders for every AR frame.

Avoid:

```js
setMarkerPosition(...)
```

inside the AR frame loop.

Do NOT update React state at 60 FPS.

Use refs or Three.js object transforms:

```js
markerRef.current.position.copy(...)
```

or the equivalent existing architecture.

React state should be used for meaningful application changes such as:

* artifact placed
* artifact selected
* curator opened
* placement confirmed

not:

* every hit-test update
* every frame
* every camera movement
* every marker position change

---

# 6. AR FRAME LOOP OPTIMIZATION

Inspect the current AR frame/update loop.

Do NOT perform expensive work every frame.

Avoid inside `useFrame`, `requestAnimationFrame`, or XR frame callbacks:

* JSON parsing
* array `.map()` over large datasets
* filtering artifacts
* creating geometries
* creating materials
* loading GLBs
* React state updates
* console.log
* DOM manipulation
* API calls
* expensive calculations

The per-frame loop should only perform lightweight operations.

For example:

```text
AR frame
 ↓
get hit-test result
 ↓
update marker position
 ↓
update marker visibility
```

Nothing more unless necessary.

---

# 7. REMOVE EXCESSIVE CONSOLE LOGGING

Search for:

```js
console.log
console.warn
console.error
```

especially inside:

* animation loops
* `useFrame`
* AR hit-test callbacks
* pointer events
* render cycles

Remove or disable high-frequency logs.

Never log every frame.

If debugging is required, throttle it.

Example:

```text
[AR] Surface detected
```

should happen only when state changes, not 60 times per second.

---

# 8. PRELOAD GLB MODELS

Inspect how GLB files are loaded.

If the same artifact is repeatedly loaded:

```text
open AR
 ↓
load model
 ↓
close
 ↓
open again
 ↓
load model again
```

fix this.

Use the existing Three.js/R3F caching mechanism where available.

If using `useGLTF`, use its built-in caching/preload behavior appropriately.

For important AR artifacts, preload when practical.

However:

DO NOT preload all 15 large models simultaneously if that causes high memory usage on mobile.

Use a balanced strategy:

```text
Currently selected artifact
        ↓
Preload / load

Nearby/likely next artifact
        ↓
Optional preload

Everything else
        ↓
Lazy load
```

---

# 9. NEVER RELOAD THE SAME GLB UNNECESSARILY

When changing:

* marker position
* marker visibility
* camera
* scale
* rotation

DO NOT reload the GLB.

The model should remain mounted.

Only update its transform.

---

# 10. OPTIMIZE GLB MODELS

Inspect all existing GLBs.

For each model, check:

* triangle count
* texture resolution
* number of materials
* number of meshes
* file size

If models are unnecessarily heavy, optimize them.

Preferred target for mobile AR:

* reasonable polygon count
* compressed textures
* minimal materials
* minimal unnecessary meshes

If appropriate, use:

```text
Draco compression
Meshopt
KTX2/Basis textures
```

ONLY if the current Three.js/WebXR setup supports them correctly.

Do not introduce compression that breaks model loading.

---

# 11. TEXTURE OPTIMIZATION

Large textures are a common mobile performance problem.

Inspect:

```text
4K textures
8K textures
```

If they are unnecessary, reduce them.

Prefer mobile-friendly texture sizes such as:

```text
1024
2048
```

depending on artifact importance.

Do not blindly reduce everything to extremely low quality.

Maintain acceptable visual quality.

---

# 12. LIGHTING OPTIMIZATION

Inspect the current lighting.

Avoid excessive lights.

Prefer a small number of efficient lights.

If possible:

```text
1 ambient/hemi light
+
1 directional light
```

instead of many dynamic lights.

Avoid expensive real-time shadows unless they materially improve the experience.

---

# 13. DISABLE EXPENSIVE SHADOWS WHERE NOT NECESSARY

Mobile AR should prioritize smoothness.

Inspect:

```text
castShadow
receiveShadow
shadowMap
```

If shadows are causing significant performance loss:

* disable them for mobile AR
* or use simplified shadows
* or use baked/static lighting where practical

Do NOT sacrifice the entire museum's visual quality unnecessarily.

Desktop and mobile can use different quality settings.

# 15. CAP PIXEL RATIO

Do not blindly use:

```js
renderer.setPixelRatio(window.devicePixelRatio);
```

on mobile.

Very high device pixel ratios can be expensive.

Use a reasonable cap such as:

```js
Math.min(window.devicePixelRatio, 1.5)
```

or another value determined by profiling.

Do not blindly copy this exact number if testing shows another value is better.

The goal is:

> prevent extremely expensive rendering on high-DPI mobile displays.

---

# 16. AVOID EXPENSIVE POST-PROCESSING

Inspect for:

* Bloom
* SSAO
* Depth of Field
* Motion Blur
* expensive outlines
* screen-space effects

Disable or reduce them in AR mode unless they are absolutely necessary.

AR should prioritize:

```text
Stable FPS
+
Low latency
+
Responsive controls
```

over cinematic effects.

# 20. SMOOTH ROTATION

Inspect the current rotate interaction.

Avoid abrupt:

```text
rotation += largeValue
```

Use smooth interpolation where appropriate.

For example:

```text
touch input
   ↓
target rotation
   ↓
smooth interpolation
   ↓
actual rotation
```

Do not introduce noticeable input latency.

Touch should still feel responsive.

---

# 21. SMOOTH SCALE

AR scaling should feel smooth.

Avoid sudden jumps when pinch zooming.

Use:

```text
currentScale
targetScale
```

and smoothly interpolate.

Clamp scale:

```text
minimum scale
maximum scale
```

to prevent the artifact becoming microscopic or enormous.

---

# 22. SMOOTH MOVEMENT

When moving the placed artifact:

```text
touch movement
 ↓
target position
 ↓
smooth interpolation
 ↓
artifact position
```

Avoid jitter.

However, do not make it so smoothed that the object feels delayed.

# 23. PREVENT UI RERENDERING FROM FREEZING THREE.JS

The AR scene and UI should be separated logically.

Opening:

```text
AI Curator
```

must not cause the entire Three.js scene to rerender unnecessarily.

Similarly:

```text
typing a question
```

must not rerender the 3D scene.

Prefer component separation:

```text
ARScene
ARControls
AICuratorPanel
```

with only the required state shared between them.

---

When the user submits:


The AR scene must remain responsive.

Do NOT:

* block rendering
* reload the GLB
* restart AR
* recreate the scene
* recreate the camera
* recreate the renderer

while waiting for the backend.

The user should still be able to look around the AR scene.
