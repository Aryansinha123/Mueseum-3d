# PHASE 1 — AI CURATOR VOICE OUTPUT (TEXT-TO-SPEECH)

## OBJECTIVE

Add a **voice output feature** to the existing AI Curator.

When the AI Curator generates an answer, the user should be able to press:

> 🔊 Listen

and hear the AI Curator's answer spoken aloud.

This must work in:

1. 🖥️ Laptop/Desktop Virtual Museum
2. 📱 Phone AR Mode

The existing RAG, Grok, artifact selection, confidence gate, source/evidence, memory, and AR functionality are already working.

**DO NOT rebuild those systems.**

This phase is ONLY:

> **AI-generated text → browser Text-to-Speech → spoken curator answer**

Do NOT implement microphone input or speech-to-text in this phase.

---

# 1. AUDIT THE EXISTING PROJECT FIRST

Before modifying anything, inspect the current implementation.

Find:

### Frontend

* AI Curator component
* Laptop AI Curator UI
* AR AI Curator UI
* Existing answer rendering
* Loading state
* Source/evidence section
* Current artifact state
* Any existing audio/voice functionality

### Backend

Do not modify the RAG pipeline unless absolutely necessary.

The backend already returns something similar to:

```json
{
  "answer": "...",
  "source": {
    "artifact": "...",
    "gallery": "..."
  },
  "confidence": 0.82,
  "evidence": "...",
  "refused": false
}
```

Use the existing `answer` field.

---

# 2. USE BROWSER TEXT-TO-SPEECH

For Phase 1, use the browser's native:

```js
window.speechSynthesis
```

and:

```js
SpeechSynthesisUtterance
```

Do NOT add an external paid TTS API.

Do NOT add ElevenLabs.

Do NOT add another AI API.

Do NOT add a backend `/tts` endpoint.

The architecture should be:

```text
Grok
  ↓
Existing RAG Answer
  ↓
Frontend receives answer
  ↓
User presses 🔊 Listen
  ↓
SpeechSynthesis
  ↓
Curator speaks
```

This keeps Phase 1 free and simple.

---

# 3. CREATE A REUSABLE TTS UTILITY

Create a reusable frontend utility rather than duplicating speech code inside every component.

For example:

```text
lib/voice/
└── textToSpeech.js
```

Use the project's existing folder conventions if a better location already exists.

The utility should provide functionality similar to:

```js
speakText(text)
stopSpeaking()
pauseSpeaking()
resumeSpeaking()
isSpeaking()
```

Do not blindly use these exact names if the existing architecture suggests better names.

---

# 4. BASIC SPEECH FUNCTION

The implementation should:

1. Check whether `window.speechSynthesis` is available.
2. Stop any previous speech.
3. Create a `SpeechSynthesisUtterance`.
4. Set the answer text.
5. Select an appropriate voice if available.
6. Speak the answer.

Conceptually:

```js
const utterance = new SpeechSynthesisUtterance(text);

utterance.rate = 0.95;
utterance.pitch = 1;
utterance.volume = 1;

window.speechSynthesis.cancel();
window.speechSynthesis.speak(utterance);
```

Do not hardcode a voice name because available voices vary by browser/device.

The button should only appear when there is an actual answer.

Do not show it during loading.

---

# 6. LISTEN BUTTON BEHAVIOR

When the user presses:

```text
🔊 Listen
```

the answer should start playing.

Change the UI while speaking.

For example:

```text
🔊 Listening...
```

or:

```text
⏹ Stop
```

Prefer providing a clear stop control.

Example:

```text
🔊 Playing
[Stop]
```

Do not allow multiple copies of the same answer to play simultaneously.

Before starting new speech:

```js
speechSynthesis.cancel();
```

---

# 7. STOP BUTTON

When speech is playing, allow the user to stop it.

Example:

```text
⏹ Stop
```

Clicking Stop should immediately call:

```js
window.speechSynthesis.cancel();
```

and return the UI to:

```text
🔊 Listen
```

---

# 8. HANDLE NEW ANSWERS

If the user asks another question while the previous answer is being spoken:

```text
Old answer
   ↓
User asks new question
   ↓
Stop old speech
   ↓
New RAG request
   ↓
New answer
```

Never allow old and new answers to speak simultaneously.

# 11. HANDLE BROWSER SUPPORT

Not every browser/device may support speech synthesis.

Check:

```js
"speechSynthesis" in window
```

If unsupported, show:

> Voice playback is not supported on this browser.

Do not crash the curator.

The text answer must continue working normally.

---

# 12. HANDLE MOBILE BROWSER RESTRICTIONS

Speech must be initiated by a user interaction such as:

```text
Tap "Listen"
```

Do NOT automatically start speech when the answer arrives.

Do NOT call speech synthesis automatically after a network response.

The user must explicitly press:

```text
🔊 Listen
```

This is important for mobile browser autoplay restrictions.

---

# 13. LANGUAGE / VOICE SELECTION

Initially use the browser's default English voice.

Do NOT build a complicated voice-selection system in Phase 1.

However, structure the utility so it can later support:

```text
language
voice
rate
pitch
volume
```

For example:

```js
speakText(text, {
  rate: 0.95,
  pitch: 1,
  volume: 1
});
```

Do not expose unnecessary settings in the UI yet.

---

# 14. SPEECH SETTINGS

Use natural museum-guide speech.

Recommended initial settings:

```text
Rate: 0.9–1.0
Pitch: 1
Volume: 1
```

Avoid robotic or extremely fast speech.

Do not modify the actual AI answer text just for speech.

The spoken text should correspond to the displayed answer.

---

# 15. DO NOT SPEAK SOURCE/EVIDENCE AUTOMATICALLY

If the response contains:

```text
Answer
Source
Evidence
Confidence
```

the default spoken content should be ONLY:

```text
answer
```

Do not automatically speak:

```text
Source: Morse-Vail Telegraph Key
Confidence: 82 percent
Evidence: ...
```

The user is listening to the curator explanation, not the UI metadata.

---

# 16. REFUSED ANSWERS

If the AI returns:

```json
{
  "answer": "This information is not available in the curated museum knowledge base.",
  "refused": true
}
```

the Listen button may still speak the refusal.

Example:

```text
🤖 This information is not available...
🔊 Listen
```

Do not attempt to generate a different answer.

---

# 17. EMPTY ANSWER HANDLING

If:

```js
answer === null
```

or:

```js
answer === ""
```

do not show the Listen button.

If somehow triggered programmatically, safely return without speaking.

---

# 18. COMPONENT LIFECYCLE

When the AI Curator component closes/unmounts:

stop active speech.

For example:

```text
Close curator
   ↓
Stop speech
   ↓
Unmount panel
```

Do not allow audio to continue unexpectedly after the curator is closed.

Also stop speech when:

* changing artifact
* leaving AR mode
* navigating away from the museum
* starting a new curator request

where appropriate.

---

# 19. ACCESSIBILITY

The Listen control should have an accessible label.

For example:

```html
<button aria-label="Listen to AI Curator answer">
  🔊 Listen
</button>
```

When playing:

```html
<button aria-label="Stop AI Curator speech">
  ⏹ Stop
</button>
```

Use `aria-live` appropriately for state changes if the existing UI already uses it.

Do not rely only on color to indicate playing state.

---

# 20. ERROR HANDLING

If speech synthesis throws an error:

Do NOT break the AI Curator.

Show a small message:

> Unable to play voice. You can still read the answer above.

The text answer must remain visible.

Do not expose browser stack traces.
