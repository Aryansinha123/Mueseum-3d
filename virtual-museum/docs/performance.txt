Optimize the existing Museum ARVR website for smooth performance and higher FPS.

IMPORTANT:
DO NOT rebuild the project.
DO NOT change the visual identity unnecessarily.
DO NOT remove existing functionality.
DO NOT break the desktop WASD/mouse museum navigation.
DO NOT break the 15 existing artifacts.
DO NOT break AR.
DO NOT replace React Three Fiber / Three.js.

The website currently feels slightly laggy/stuttery, especially because it contains 3D GLB museum artifacts.

The goal is:

- smooth desktop museum navigation
- stable FPS
- fast initial load
- smooth artifact interaction
- smooth camera movement
- lower memory usage
- smooth mobile performance
- AR should remain lightweight

==================================================
PHASE 0 — PROFILE BEFORE MODIFYING
==================================================

First inspect the current implementation and identify the actual performance bottlenecks.

Inspect:

- package.json
- src/data/artifacts.json
- all museum/gallery components
- ArtifactManager
- Artifact
- AutoFitModel
- GLB loading components
- lighting
- shadows
- Canvas configuration
- camera
- controls
- post-processing
- animations
- React state
- AR components

Do NOT immediately optimize by guessing.

Create a short performance diagnosis:

1. number of GLBs loaded simultaneously
2. approximate number of meshes
3. approximate triangle count if available
4. texture sizes
5. number of lights
6. shadow configuration
7. renderer configuration
8. unnecessary React re-renders
9. expensive per-frame calculations
10. duplicated model loading

Then optimize based on the findings.

==================================================
PHASE 1 — LAZY LOAD ARTIFACTS
==================================================

Do NOT load all 15 GLB models unnecessarily.

Use lazy loading.

Only load an artifact when it is actually needed/visible.

Preferred strategy:

Museum
  ↓
Gallery
  ↓
Visible artifacts
  ↓
Load required GLBs

Do NOT preload every high-cost model during initial page load.

Keep artifact metadata lightweight.

The artifact metadata should load immediately, but the actual GLB should load only when required.

Use Suspense/loading boundaries properly.

==================================================
PHASE 2 — CACHE GLB LOADS
==================================================

Ensure the same GLB is not fetched and parsed repeatedly.

Use the existing R3F/drei loading mechanisms where appropriate.

If useGLTF is already used, use its caching behavior correctly.

Do NOT create duplicate GLTFLoader instances unnecessarily.

If an artifact is revisited, it should reuse the cached model where possible.

==================================================
PHASE 3 — MODEL OPTIMIZATION
==================================================

Inspect the actual GLB models.

For each model determine:

- triangle count
- number of meshes
- texture resolution
- material count

Do NOT automatically simplify every model.

Preserve visual quality while reducing unnecessary rendering cost.

Priority:

1. reduce excessive geometry
2. reduce excessive texture resolution
3. reduce unnecessary materials
4. remove hidden/unused objects if safe

The artifacts are museum exhibits, so visual quality must remain acceptable.

Do not damage recognizable artifact shapes.

==================================================
PHASE 4 — TEXTURE OPTIMIZATION
==================================================

Large textures can cause major GPU memory usage.

Inspect textures in the GLBs.

If textures are unnecessarily huge, optimize them.

Prefer appropriate compressed/resized textures.

For museum models:

- avoid unnecessary 4K/8K textures
- use 1K/2K where visually sufficient
- preserve important surface details

Do not reduce textures blindly.

If existing GLBs cannot easily be modified, document which models are texture-heavy instead of corrupting them.

==================================================
PHASE 5 — SHADOW OPTIMIZATION
==================================================

Inspect all shadow settings.

Avoid expensive shadow rendering for every artifact.

Use simple lighting.

Prefer:

- one main directional light
- limited ambient/fill lighting
- controlled shadow casting

Do NOT use expensive shadow settings unnecessarily.

If PCFSoftShadowMap is still present, update deprecated configuration appropriately.

The previous warning:

THREE.WebGLShadowMap:
PCFSoftShadowMap has been deprecated.

must be removed.

Use the current supported shadow map configuration.

Do not add expensive real-time shadows to every artifact.

Where possible:

- only important lights cast shadows
- only important objects cast/receive shadows
- use reasonable shadow map resolution

==================================================
PHASE 6 — RENDERER OPTIMIZATION
==================================================

Inspect the <Canvas> configuration.

Optimize only after profiling.

Consider appropriate settings for:

- antialias
- pixel ratio
- shadows
- tone mapping
- output color space
- power preference

Do NOT force unnecessarily high devicePixelRatio.

For high-DPI phones, rendering at full native DPR can be expensive.

Use a sensible capped DPR.

Conceptually:

desktop:
reasonable DPR cap

mobile:
lower DPR cap

The visual difference should be minimal but performance improvement significant.

==================================================
PHASE 7 — CAMERA AND CONTROLS
==================================================

Ensure camera movement does not trigger unnecessary React renders.

WASD and mouse look should operate smoothly.

Do NOT store continuously changing camera position/rotation in React state.

Avoid patterns like:

setState(camera.position)

on every frame.

Use refs / Three.js objects for per-frame values.

The existing PointerLockControls behavior must remain unchanged.

==================================================
PHASE 8 — USEFRAME OPTIMIZATION
==================================================

Inspect every useFrame().

This is extremely important.

Find expensive calculations running every frame.

Avoid:

- object allocation inside useFrame
- new Vector3() every frame
- new Quaternion() every frame
- repeated Box3 calculations
- repeated model traversal
- repeated raycaster creation
- React setState inside useFrame
- repeated expensive math that can be calculated once

Move static calculations outside useFrame or cache them.

Bad:

useFrame(() => {
    const box = new THREE.Box3();
    ...
});

Better:

create/cache once and reuse.

==================================================
PHASE 9 — AUTOFIT MODEL OPTIMIZATION
==================================================

Inspect AutoFitModel.

Do NOT calculate bounding boxes every frame.

Bounding box / normalization should happen:

- once when model loads
- or once when model changes

Cache:

- bounding box
- dimensions
- scale
- center
- bottom offset

Do not continuously traverse the GLB hierarchy.

==================================================
PHASE 10 — REACT RENDER OPTIMIZATION
==================================================

Find unnecessary component re-renders.

Use:

- React.memo
- useMemo
- useCallback

where they actually help.

Do NOT wrap every component in memo blindly.

Especially optimize:

- Artifact
- ArtifactManager
- gallery components
- HUD
- artifact info
- map
- selection UI

A UI state change should not cause every 3D artifact to rerender unnecessarily.

Separate:

UI state

from:

Three.js scene state.

==================================================
PHASE 11 — VISIBILITY / FRUSTUM
==================================================

Do not perform expensive work on artifacts that are not visible.

Use sensible visibility handling.

If the museum has artifacts in different rooms/galleries:

only keep expensive rendering active for the current/nearby gallery where practical.

Do not destroy everything unnecessarily because reloading models causes another performance problem.

Use a balanced strategy:

current gallery:
active

nearby/simple:
lightweight or cached

far/inactive:
not rendered if safe

==================================================
PHASE 12 — GALLERY MANAGEMENT
==================================================

The museum contains:

- Space Gallery
- History Gallery
- Natural History Gallery

Do not make all galleries equally expensive at all times.

If entire gallery scenes are currently mounted simultaneously, evaluate whether inactive galleries can be:

- hidden
- suspended
- or unloaded when appropriate

Do not break map teleportation.

When teleporting to another gallery:

load the required content smoothly.

Show a small loading indicator if necessary.

==================================================
PHASE 13 — LOADING EXPERIENCE
==================================================

Never freeze the UI while a large GLB loads.

Show:

Loading artifact...

or

Loading gallery...

Use the existing LoadingScreen/Suspense infrastructure if possible.

Avoid blocking the entire application unnecessarily.

The user should still see a responsive UI while assets load.

==================================================
PHASE 14 — ARTIFACT INTERACTION
==================================================

Ensure artifact hover/click/selection does not cause expensive scene-wide updates.

Selection should affect only the relevant artifact/UI.

Do not update every artifact's state every frame.

==================================================
PHASE 15 — AR PERFORMANCE
==================================================

AR is more performance-sensitive than desktop.

Create an AR performance mode.

When AR is active:

- lower DPR if necessary
- disable unnecessary shadows
- disable expensive post-processing
- use lightweight lighting
- load only the selected artifact
- avoid loading all 15 models
- minimize UI animation
- avoid unnecessary scene objects

AR should load:

Selected artifact only

NOT:

all 15 artifacts.

==================================================
PHASE 16 — MOBILE RESPONSIVENESS
==================================================

Detect mobile capability carefully.

Do not assume every phone has the same GPU.

Use reasonable performance tiers.

Example:

HIGH:
desktop / powerful device

MEDIUM:
normal mobile

LOW:
weak mobile

Adjust only expensive rendering settings.

Do not significantly degrade visual quality on desktop.

==================================================
PHASE 17 — REMOVE DEVELOPMENT OVERHEAD
==================================================

Check for:

- excessive console.log
- debug rendering
- development-only overlays
- repeated logging
- unnecessary network requests
- duplicate API calls

Remove or gate them appropriately.

Do not remove useful error handling.

==================================================
PHASE 18 — NETWORK PERFORMANCE
==================================================

Inspect model loading.

Ensure:

- GLBs are requested only when needed
- duplicate requests do not happen
- metadata is not fetched repeatedly
- unnecessary API calls are avoided

If possible, verify browser Network tab behavior.
